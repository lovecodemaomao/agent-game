# Design: sim-platform-and-agents

## Context

全新 Python 项目（空仓库，只有比赛材料 `docs/` 与 LLM 密钥 `deepseek-key.md`）。系统必须以《接口文档》为唯一协议权威：demo request/response 是报文格式的验收基准。赛制硬约束：判题器 5 秒响应死线、单队 5 次异常淘汰、每游戏日 3 次 LLM 配额（任务期豁免）、沙盒 15 秒/无外网。LLM 只在开发期可得（deepseek-v4.1-flash），比赛期由平台提供——因此 agent 内部 MUST NOT 直连任何 LLM API，一切 LLM 交互经 `prompt` 字段由判题侧转发。三个 LLM 调用上下文（我方 agent / 中立新闻 / 对手 agent）互不互通。

## Goals / Non-Goals

**Goals:**
- 一条命令跑通完整对战：判题循环拉起双方 agent → 跑满一场 → 输出对局记录 → 前端可回放
- 协议零偏差：出站校验器保证双方 agent 全场无"指令错误"级非法报文；引擎产生的 request 与 demo request 字段级一致
- 未定义机制全部参数化（机器人寻路/波次/新闻影响等），支持扫描而非单点假设
- 我方 agent 的策略内核（OpponentModel + 教义×旋钮 + 每日 LLM 分析）可独立于引擎单测

**Non-Goals:**
- 批量参数扫描与自进化养库（教练 LLM、k-NN 推荐表）——后续变更
- 对手 agent 的每日策略调整——本变更固定策略卡
- 比赛环境真机对接（内网 LLM API、真实判题器）——预留适配层但不实现
- 沙盒的强安全隔离（容器级）——本地开发以子进程+超时+禁网标记近似

## Decisions

### D1 项目结构与进程拓扑

```
agent-game/
├── run.sh                      # 统一入口: 启动一场对战
├── config/
│   ├── engine.yaml             # 地图/波次/寻路/新闻影响等未定义机制参数
│   ├── doctrines/              # 教义预设卡 (JSON 参数向量)
│   └── baselines/              # 对手基线策略卡
├── sim/                        # 模拟平台（扮演判题器+中立系统）
│   ├── engine/                 # 战斗引擎 (纯函数式核心+状态)
│   ├── judge/                  # 判题循环/HTTP客户端/异常计数/对局记录
│   ├── llmproxy/               # deepseek 客户端/三上下文隔离/每日配额
│   ├── sandbox/                 # 每队子进程沙盒/mock任务API
│   ├── news/                   # 新闻系统 (事件参数先行+LLM措辞)
│   └── web/                    # 前端静态服务与对局记录API
├── agents/
│   ├── framework/              # 公共骨架: server/编排/校验器/任务代理
│   ├── competitor/             # 我方agent (main入口)
│   └── baseline/               # 对手agent (main入口)
└── tests/
```

进程拓扑：判题循环为主进程，拉起两个 agent 子进程（各监听端口）+ 两个沙盒子进程，全部本地回环。备选方案"全单进程函数调用"被否决：HTTP 边界正是比赛真实边界，绕过它测不出协议缺陷（超时/格式错误/异常计数全部失真）。

### D2 战斗引擎：确定性核心

引擎 = 纯状态对象 + 逐回合 step(request 双方 response, news) → 新状态 + 回合事件流。关键点：
- **结算顺序固定**：眩晕/炸弹物品 → 武器攻击（伤害延迟到回合末统一结算）→ 机器人移动 → 角色移动碰撞（目标受阻/争夺/互换三情形）
- **可见性计算独立成纯函数**：`compute_request_view(state, team) → request JSON`，直接以 demo request.txt 做快照验收（字段级 diff）
- **未定义机制 = 配置注入的策略对象**：机器人寻路（直线撞墙/BFS 绕障）、波次表、出生点分布、新闻价格倍率曲线、宝藏谜题模板、任务超时回合数——每个都是 `config/engine.yaml` 显式声明 + 引擎侧接口化，禁止散落硬编码
- 角色 ID 按《接口文档》分配表在初始化时固定；机器人 ID 从 30001 递增
- 技术选型：纯 Python 无第三方依赖（引擎不碰网络/LLM），保证可复现性与测试速度

### D3 判题循环与 LLM 代理

- HTTP 客户端用 `requests`，对每个 agent 的每回合请求带死线（连接 10s/响应 5s，与赛制一致；本地可用配置放宽便于调试，但默认值必须是赛制值）
- **LLM 代理的关键设计**：prompt 的发送方不等待 LLM 完成。判题循环收到含 `prompt` 的 response 后异步发起 deepseek 调用，结果写入该队 pending 槽，下一回合组 request 时回填 `llmResp`。配额计数在发送时扣减（任务期豁免由引擎的任务状态机判定）
- **三上下文隔离**：LLM 代理按 `(team, purpose) ∈ {我方agent, 新闻, 对手agent}` 维护三个独立会话存储，消息历史互不可见；新闻系统的调用由引擎日界触发而非 agent 发起
- **异常计数**：三类异常（超时/格式错误/指令错误）计入 `abnormalCount[field]`；`指令执行失败`（碰撞/落点无目标）只标记 `lastRoundRoleActionResults[key]=false`。达 5 次停止调度该队
- **对局记录**：逐回合 append JSONL（双方 request/response 原文 + 引擎事件流 + 积分快照），作为前端回放的唯一数据源

### D4 新闻系统：参数先行，LLM 措辞

避免"LLM 自由发挥导致影响不可计算"的问题：**先确定性采样事件参数**（矿种/影响天数/价格倍率/可采性 + 宝藏谜题答案三元组），**再让 LLM 把参数"写"成叙事文本**（独立上下文、prompt 中给参数与风格要求）。文本只需"可推断"参数，引擎按参数真实结算。这样：新闻的地面真值可控、可测试；LLM 只承担措辞任务，弱模型也稳定。备选"纯 LLM 生成后反向解析"被否决——解析失败无兜底，且无法保证谜题线索链收敛。

### D5 agent 公共骨架：校验器是生命线

```
策略层产出 → [出站校验器] → response
              1. schema: action∈动作码全集; 必填字段齐备(move/build/.../attack
                 都要 targetPos; sell/buy/use/drop 要 name; attack 要
                 controllerId; summonTreasure 要 targetPos+item; buy/sell
                 的 num 数值类型)
              2. 语义: 坐标∈[0,40]×[0,31]; ID 归属本队; 昼夜门(白天禁 attack/
                 build); 角色类型门(工人才能 build/collect; 开拓者才能
                 acceptTask); 多目标数量=武器等级; 加特林锥形≤90°
              3. 兜底: 非法指令剔除该条(不出站); 整体异常→空 roleCommandMap
```

校验器纯确定性、零 LLM，双方 agent 共用同一实现（`agents/framework/validator.py`），单测覆盖每个动作码的合法/非法样例。**语义门只做"静态可判定"的规则**（不依赖引擎状态的部分），避免 agent 侧重复实现引擎逻辑产生双份真相；依赖实时状态的合法性（如目标点是否被占）交给引擎，失败只算"指令执行失败"不计异常，风险可控。

### D6 agent 编排：时限内必答

收到 request → 上下文更新（WorldModel/OpponentModel diff）→ 策略计算 → 校验 → 返回。单回合计算设内部时间预算（默认远小于 5 秒），超预算立刻返回已有结果（角色粒度部分提交）。任何未捕获异常走兜底空响应。不采用"先返回后计算"——本地延迟可控，且立即返回会让测试对慢计算不敏感；保留该模式作为配置项以便将来贴近真实时序。

### D7 我方 agent 内核

- **OpponentModel**：逐回合对三条全局通道做 diff（敌方建筑列表/等级/血量、机器人列表及血量、矿价货架），输出动作事件流 + 滚动特征（围墙增速、击杀 DPS 指纹、骚扰强度、任务活动推断）。全部纯函数，可用引擎对局记录离线回放验证
- **教义×旋钮**：`DoctrineParams` 数据类（~15 旋钮，含硬 min/max），预设卡 JSON 热加载；引擎按当前参数向量决策日常调度，零 LLM
- **每日 LLM 分析**：日界第一回合发合并 prompt（仪表盘 + 教义索引 + 新闻），次回合读 `llmResp` → JSON schema 校验 → 夹紧 → 原子替换当日参数。日界当天用昨日教义顶班（`llmResp` 一回合延迟的固有补偿）。兜底链：LLM 结果 → 昨日教义 → 全局默认
- **任务代理**：`phaseTask` 出现即进入任务态——LLM（无限额）与沙盒流水线并行：prompt 思考/生成命令，executeCmd 执行/探测，SOP 脚本沉淀在沙盒家目录（跨任务持久性作为第一个任务的首个实验：写标记文件验证）

### D8 对手基线 agent

复用 framework 全部基建（server/校验器/任务代理），策略层为单张策略卡（如龟缩流：满围墙迷宫+3 加特林+不骚扰）。非任务期 prompt 恒为空；接受新闻但不分析（规则化忽略）。确定性可复现：策略卡不依赖随机源（或固定种子）。

### D9 前端：回放优先

`sim/web/` 用 Python 标准库 http.server 提供静态页 + 两个 API（对局列表 / 单场 JSONL），页面为单文件 HTML+Canvas+原生 JS（无构建链）。地图 41×32 Canvas 网格渲染，单位按 roleType 着色；回合步进时叠加动作箭头/标记与有效性；侧栏资源面板 + 积分曲线（Canvas 折线）+ 过滤式事件日志。**回放数据完全来自对局记录文件**，前端不依赖引擎进程——先跑赛后看，也支持判题循环推送的实时模式（轮询 JSONL 增量）。

### D10 LLM 客户端与密钥管理

deepseek-v4.1-flash 经 OpenAI 兼容接口 + `requests` 调用；密钥从仓库 `deepseek-key.md` 读取（加入 `.gitignore` 防误提交；仓库里保留 `deepseek-key.example.md` 模板）。客户端含重试（指数退避×2）、超时（60s）、简单磁盘缓存（同 prompt 去重，开发期省额度）。三上下文在代理层各持独立 messages 历史。

## Risks / Trade-offs

- [任务书未定义机制与真实判题器不一致] → 全部参数化并预置多档默认；防御布局按多档扫描取鲁棒而非单点最优
- [深抠协议仍可能漏corner case] → 以 demo request/response 做验收快照 + 校验器单测覆盖每个动作码；对局记录含原始报文便于事后审计
- [deepseek 延迟/额度拖慢模拟] → LLM 调用异步化 + 磁盘缓存 + 新闻预生成（开赛前批量生成 10 天）；断点续跑（对局记录 + 状态快照）
- [沙盒禁网在本地无强制力] → 开发期以环境变量标记 + mock API 路由近似；行为纪律写入任务代理（不得访问真实外网域名）
- [双 agent 共用校验器可能掩盖"对手实现差异"] → 校验器是骨架层共用（协议层），策略层完全分离；这是刻意决策：比赛淘汰规则面前，协议合规不该是对手差异点
- [引擎复杂度（碰撞/攻击结算边界多）] → 结算顺序文档化 + 逐机制 golden 测试（固定输入状态→断言输出状态）

## Migration Plan

新项目无存量迁移。分期落地（每期可独立验证）：
1. **P0 协议闭环**：framework（server+校验器）+ judge（HTTP 循环+记录）+ demo 报文回放验收
2. **P1 引擎可战**：引擎核心 + 基线 agent（固定卡）→ 一场 10 天完整对战 + 前端回放
3. **P2 LLM 全链路**：llmproxy（三上下文+配额）+ 新闻系统 + 沙盒 + 我方 agent 任务代理
4. **P3 智能内核**：OpponentModel + 教义×旋钮 + 每日 LLM 分析 → 我方 vs 基线对战复盘
回滚 = 停用新模块开关，系统退回上一期形态。

## Open Questions

（12.4 已回填实测结论：✔=已实测/已定型；⚠=需比赛环境复核。）

1. ✔ `attack` 挂载键：按 demo response.txt 实现（武器 ID 为键 + `controllerId` 标注操控角色），校验器与引擎双向对齐。⚠ 真实判题器若相反，仅需改 view/validator 两处。
2. ✔ 武器仅攻击机器人（任务书只描述打机器人）；对建筑/角色的攻击语义预留参数化位。
3. ✔ 沙盒文件系统跨任务/跨进程持久 = YES（tests/test_taskagent 10.4 实测：任务 A 写入的脚本与标记文件任务 B 可读）。注：agent 侧 SOP 记忆为进程内，跨进程重启需一个探针回合（`test -f sop_weather.sh`），已记录为已知限制。
4. ✔ `submitAnswer` 可多次提交、超时取最高通过率（按任务书 1.3.2 措辞实现；引擎测试确认错误答案不结束任务）。
5. ✔ 机器人波次公式：参数化 `wave_formula` + `wave_scale`（默认 1.0，扫描用 0.5/2.0），每日波次 = (a + b×day)×scale。
6. ✔ 任务点任务总数上限：参数化 `per_point_total`，默认每点 5 个。
7. ✔（实施中新发现）demo request.txt 的攻击距离（加特林 L1=4、狙击 L1=7、火箭 L1=全图）与任务书 4.5.1（3/6/10）矛盾——采用任务书数值为权威，golden 对比按字段结构对比（不含数值），风险记录在案。
8. ✔（实施中新发现）docs/request.txt 与 response.txt 存在 JSON 书写瑕疵（尾逗号、缺逗号），测试与加载使用宽松解析器（tests/util.py），docs 原文件保持只读。
9. ✔（实施中新发现）LLM 每日分析的异步回填为"单槽"设计：新 prompt 会覆盖未完成槽位；慢响应可能跨日到达——回填内容经 schema 校验+夹紧，过期分析无害。缓存命中时端到端 2 回合内完成（e2e 实测 4/4 全部按期回填）。
